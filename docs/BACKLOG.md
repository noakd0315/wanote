## 🔴 輸出コンプライアンス（要調査・実登録前に決着させること）

**PM判断: 2026-08-16、その場で答えず調査フェーズを設けることにした。**

TestFlight にビルドを配信するだけでも、`ITSAppUsesNonExemptEncryption`
（またはApp Store Connect上の同等の設問）への回答が要る。実登録では
避けて通れない。

### なぜ即答できないか

Apple の設問は、書類提出が必要な条件をこう書いている。

> 標準的な暗号化アルゴリズム（Appleのオペレーティングシステム内の暗号化を
> 使用したり、それにアクセスをしていないアルゴリズム）

このアプリの実態:

| | 判定 |
|---|---|
| 独自・非標準のアルゴリズム | **無し**（自前実装はゼロ） |
| `flutter_secure_storage` | iOSキーチェーンを使用 → 該当しない |
| HTTPS/TLS 全般 | 通信保護のみ |
| 🔴 **Firebase SDK（特に Firestore）** | **gRPC/BoringSSL を同梱**しており、Apple のネットワーク層をそのまま使っていない |

最後の1行が論点。**「標準アルゴリズムだが Apple OS の暗号化ではない実装」**
に文言上は当てはまり得る。Firebase を使うアプリの大半は免除として申告して
いるが、それは慣行であって、設問を厳密に読むと自明ではない。

### 決着させるべきこと

- [ ] 免除に該当するか（該当類型：「認証のためだけの使用」等）
- [ ] 該当するなら `ITSAppUsesNonExemptEncryption = false` を `Info.plist` へ
      （毎ビルドの質問が消え、CIがそのまま配信できる）
- [ ] 該当しないなら **CCATS または ERN の取得**。BIS への申請で**数週間**
- [ ] フランス市場に出すなら別途宣誓書

### 日程への影響

🔴 **書類が必要と判断した場合、取得に数週間かかる。** 9/30 の締切から逆算
すると、**Play の「12人×14日」と並ぶ律速になり得る。** 実登録の直前に着手
すると間に合わない。

**これは輸出規制の法的申告であり、PMの責任範囲。** 判断がつかない場合は
Apple のサポートか専門家に確認すること。

## Firebase の Web アプリ登録をいつ消すか（2026-08-18 記録）

Firebase プロジェクトに **Web アプリ**（`1:715210245467:web:...`）が登録されている。
開発中、Windows 上で `flutter run -d chrome` を使って画面を確認するために作った
もので、**配信物ではない**。

### 消してよいタイミング

**内部テストと審査が完全に終わってから。** それまでは残す。理由:

- `lib/firebase_options.dart` に `web` の設定が残っており、`kIsWeb` の分岐から
  参照される。消すと Web でのデバッグ実行ができなくなる
- 現在も画面確認の最速手段が Chrome 実行である（実機ビルドは数分かかる）

### 消すときにやること

1. Firebase コンソール → プロジェクトの設定 → 「マイアプリ」から Web アプリを削除
2. `flutterfire configure` を再実行して `firebase_options.dart` を再生成
   （`web` の項目が消える）
3. `kIsWeb` 分岐を持つコードの整理:
   - `lib/shared/config/auth_emulator_seed_web.dart`
   - `lib/shared/config/backend_config.dart`（ローカル開発用フォールバック）
   - `AdManager.platformSupported` / `ReminderNotificationAdapter.platformSupported`
4. `web/` ディレクトリの削除を検討（残しても配信物には含まれない）

### 消さなくても実害はあるか

**ストア配信・審査への影響はない。** Web アプリの登録は Firebase 内部の話で、
Play / App Store からは見えない。**急いで消す必要はない。**

ただし Firebase の Web API キーは `firebase_options.dart` 経由でアプリの
バイナリに含まれる。Web アプリを残す限り、そのキーも残る。
セキュリティは Firestore/Storage ルールで担保しているため問題にはならないが、
**使わないものは消しておく方が、後から見た人が迷わない。**

## リリース後のアップデート用テストデータ環境（2026-08-18・PM提起）

**PM 指摘: アップデートに向けたテストデータ環境が無いのはまずい。**
現状、開発中の動作確認は**本番 Firebase プロジェクト（`wanote-7dca0`）**の
データで行っている。公開後は、ここに**実利用者のデータが入る**。

### 何がまずいか

- **実利用者のデータを見ながら開発することになる。** 医療情報を扱うアプリで、
  プライバシーポリシーにも書いていない扱い方になる
- 検証のために作ったゴミデータが本番に混ざる
- 破壊的な検証（アカウント削除・データ移行）が本番でしかできない
- Firestore のルール変更やインデックス追加を、**本番で試すことになる**

### 選択肢

**案A: Firebase プロジェクトを分ける（推奨）**
`wanote-dev` を新規作成し、開発・検証はそちらへ向ける。
- `--dart-define-from-file=config/dev.json` で切り替える仕組みは既にある
- `firebase_options.dart` を環境ごとに持つ必要があり、`flutterfire configure`
  の運用を整理する必要がある
- Worker も dev 用に分ける（Cloudflare の環境またはワーカー名を分ける）
- **費用**: Firebase の無料枠内で収まる見込み

**案B: エミュレータを使う**
`firebase.json` にエミュレータ設定は既にある（Auth/Firestore/Storage）。
- 追加費用ゼロ、ネットワーク不要
- ただし **RevenueCat と AdMob と Anthropic は繋がらない**ので、
  課金・広告・AI の検証はできない

**現実的には A と B の併用。** 日常の画面確認は B、
課金や AI を含む通し確認は A。

### いつやるか

**公開前にやるのが理想だが、公開を遅らせてまでやるものではない。**
公開直後、実利用者がまだ少ないうちに着手するのが現実的。

**着手の判断材料**: 実利用者が1人でも入った時点で、本番での検証は
「他人のデータがある場所で作業する」ことになる。そこが分岐点。

# ~~AI の回答が Markdown のまま表示される~~ → **対応済み（2026-08-19）**

登録: 2026-08-19（ストア用スクリーンショットの撮影中に発見）

## 症状

AI の回答が**記法のまま**画面に出る。実際に出た文字列:

```

体重4.8kgの成犬であれば、114g/日を**2〜3回に分けて与える**ことをお勧めします。

**配分例：**
- 2回食：朝57g、夜57g
```

`#` と `**` がそのまま読める状態で、**AI 機能全体に影響する**。

## 原因

回答を素の `Text` / `SelectableText` に流しているだけで、整形も除去もしていない。

| 画面 | 箇所 |
|---|---|
| 給餌アドバイス | `lib/features/ai/presentation/food_portion_screen.dart:555` |
| AI相談 | `lib/features/ai/presentation/consultation_screen.dart:357` |

プロンプト側にも「Markdown を使うな」の指示がない（`functions/src` を確認済み。
`ocrParsing.ts` だけが `no markdown fences` と書いているが、これは JSON 用）。

## 対応案

| 案 | 内容 | 評価 |
|---|---|---|
| A | プロンプトに「plain text で答える」を追加 | 安いが、モデルは時々破る。**単独では不十分** |

| C | Markdown として描画する | 本筋。ただし `flutter_markdown` は 2025 に開発終了しており、

**推奨は A＋B を先に入れ、C は後日。** 公開前に A＋B だけでも入れる価値がある
（AI はこのアプリの差別化点で、いま一番みすぼらしく見える箇所）。

# ~~ホームのショートカットが反応しないことがある~~ → **原因特定・修正済み（2026-08-19）**

登録: 2026-08-19（PM報告。**再現には成功、原因未特定**）

## PM報告

「画面操作をして、ホーム画面のショートカット押下で、指定画面に飛ばない事象に
何回も遭遇しています。」

（当初はリマインダー通知との関連を疑ったが、**PMより因果関係は無いと確認済み**。
この線は取り下げ。）

## 再現実験（実機 SH-RM15 / Android 12）

ホーム → ショートカット を 4種 × 8ラウンド = **32回**自動実行し、
遷移後のスクリーンショットをホームのベースラインと比較した。

```
trials  : 32
failures: 6      ← 画面がホームのまま（差分 0.0 = 完全一致）
  r1_weight  r1_toilet  r1_cert  r1_food
  r2_weight  r2_toilet
```

**失敗はラウンド1〜2に集中し、3〜8では0件。**
アプリを前面に出してから**最初の30〜40秒だけ**起きている。

失敗した4種類すべてで起きているため、**「餌の量」固有の問題とは別**
（そちらは `_openFoodPortion` の無制限 await として別途修正済み）。

## 未検証の仮説

| # | 仮説 | 備考 |
|---|---|---|
| A | 起動直後は何かがタップを吸っている（`AdBackdrop` などの全画面オーバーレイ） | `ad_backdrop.dart` は自壊タイマー付きだが、起動直後の挙動は未確認 |
| B | `IndexedStack` の各セクションが初期化を終えるまで、`tabRequest` が届いても反映されない | `_applyTabRequest` は `initState` でも呼ばれるが、`TabController` 生成前後の順序は未確認 |
| C | `didChangeAppLifecycleState` の resumed リセットが遅れて届く | 1回のresumeで6回失敗する説明にはならず、**単独では不十分** |

## 原因（確定）

**PM の見立てどおり、スワイプ対応で埋め込まれた。**

`keep_alive_tab.dart` のコメントに経緯が残っている:

> The sections used an IndexedStack ... Swapping to TabBarView is what
> makes the tabs swipeable (PM request, 2026-08-18).

`_openSectionTab` は**タブを指定してから**セクションを表示していた。

```dart
tabRequest.value = tabIndex;          // ← まだ Home が映っている
setState(() => _selectedIndex = ...); // ← ここで初めて表示される
```

**IndexedStack のころはこれで動いた。** 同期的に子を差し替えるだけで、
描画されているかどうかを問わないため。

**TabBarView は PageController を介してアニメーションする。**
Home の裏に隠れたままの TabBarView に「隣のタブへ動け」と言っても動かず、
表示された時点では元のタブのまま。だから**そのタブを以前に開いていた
ときだけ**失敗する（開いていなければ移動が不要なので成功に見える）。

**PM 報告の再現手順**

```
健康の記録を表示 → ホーム → 体重（ショートカット） → 健康の記録が出る
通院履歴を表示   → ホーム → 証明書（ショートカット） → 通院履歴が出る
```

**「トイレの方が正しく動くことが多い」も説明がつく。**
Flutter は隣接タブを animate、離れたタブを jump してから animate する。

# 【アップデート候補】写真と基礎情報から BCS を判定する

登録: 2026-08-19（PM相談。**実装しないことを確認済み。公開後のアップデート項目**）

## やりたいこと

愛犬の写真とプロフィール（犬種・体重・年齢）から、**BCS（ボディコンディション
スコア）を AI に推定させる**。給餌量計算の「体型」入力につなげる。

## 技術的には可能。ただし「判定」と呼べるかは別問題

**BCS は本来「触って」決めるもの。** アプリ自身の説明文がそれを言っている
（`foodPortionBodyConditionHelperText`）:

```
あばら骨に触れやすい＝痩せ気味／触れるが見えない＝標準／触れにくい＝ぽっちゃり気味
```

**3つの基準すべてが「触れるかどうか」。写真は触れない。**

WSAVA の判定は概ね3点を見る:

| 基準 | 写真で分かるか |
|---|---|
| 上から見たときのくびれ | ✅ |
| 横から見たときの腹部の吊り上がり | ✅ |
| **肋骨の触感（脂肪の厚み）** | ❌ **不可能** |

3分の2までしか届かず、**残り1つが獣医の最重視項目**。

## 精度を落とす要因

- **被毛**（最大の敵）。長毛種は体型が毛で完全に隠れる。
  **wanote のロゴ犬がロングコートダックスであることに注意**。
  ポメラニアン、シェルティ等も同様で、機能しない層が相当数いる
- **角度**。くびれは真上から、吊り上がりは真横から。片方では材料不足
- **姿勢**。立っていない／伸びている／寝ている、でいずれも崩れる
- **犬種の基準差**。イタグレは健康でも肋骨が見え、フレブルは標準でも
  くびれが出ない。**犬種を渡さないと系統的に間違える**

## 🔴 誤判定の害の方向

**「ぽっちゃり」と誤ると飼い主は餌を減らす。**
wanote は給餌量計算とつながっているので、誤った体型がそのまま
**1日の給与量を減らす方向に効く**。標準体型の犬が減量させられる。

逆方向（痩せ気味と誤って増やす）より**こちらの害が大きい**。
特に高齢犬や闘病中の犬では危険。

ストア審査でも、医療的な判定を自動で出す機能は説明を求められやすい。

## 設計方針：「判定」ではなく「入力の補助」にする

| | 判定として出す | **入力の補助として出す（採用案）** |
|---|---|---|
| 表現 | 「BCS 6/9です」 | 「標準〜ぽっちゃり寄りに見えます。**肋骨を触って確かめてください**」 |
| 給餌計算への反映 | 自動 | **必ず本人の確認を挟む** |
| 外れたとき | アプリの誤り | 参考情報の1つ |

体型ドロップダウンの隣に「写真から候補を出す」を置き、AI は
**候補をプリセットするだけ**。決定権は飼い主に残す。

## wanote ならではの補強：体重履歴で裏を取る

AI が「ぽっちゃり」と言っているのに**体重が安定していて犬種の標準範囲内**なら、
**食い違いを表示する**。逆に一致すれば確信度を上げる。

**競合が持っていない使い方。** 記録アプリであることの強みがそのまま効く。

## 実装するときの最低要件

1. **撮影ガイド**（上から1枚・横から1枚。シルエットの重ね表示があると成功率が上がる）
2. **犬種を必ずプロンプトに渡す**（プロフィールに既にある）
3. **長毛種は結果を弱める**（「毛で隠れているため参考程度です」を明示）
4. **単一の数値ではなく幅と確信度を返す**

技術的には既存の OCR 経路とほぼ同じで、Haiku 4.5 の vision をそのまま使える。
**コストは1回あたり数円未満**、AI相談チケットの枠に載せられる。

## 時期の判断（2026-08-19 PM 決定）

**公開を先に終わらせ、これは公開後のアップデートに回す。**

デモ映えは非常に良く Shipaton へのアピールにはなるが、撮影ガイド UI まで
含めると小さくない実装で、精度の作り込みには実データでの試行錯誤が要る。
**中途半端な精度で出すと、医療情報アプリとしての信頼を最初に傷つける。**

# 【公開前に必須】配信地域を日本・米国に絞る

登録: 2026-08-20（PM判断で**テスト設定を優先**し、後回しにした）

## やること

**アプリ本体と商品は別々の設定。** 片方だけだと「アプリは入れられるのに
プランが買えない」状態になり、低評価に直結する。

### iOS

| 対象 | 場所 | 状態 |
|---|---|---|
| サブスク単体の販売地域 | サブスクリプションの編集画面 → **販売地域（Availability）** | 🔴 未 |
| アプリ本体の配信地域 | **価格および配信状況** → **国または地域** | 🔴 未 |

**価格が全世界分で自動計算されていても、販売地域とは独立している。**
自動計算は「もし売るならこの額」というだけ。販売地域で絞れば売られない。

### Android

| 対象 | 場所 | 状態 |
|---|---|---|
| 商品の販売地域 | 基本プランの **地域と価格を設定** | ✅ 済（日米のみ価格を入れた時点で他地域は対象外） |
| アプリ本体の配信地域 | リリース → **製品** → **国 / 地域** | 🔴 未 |

## 🔴 なぜ EU を外すのか

**金額の問題ではない。**

EU のデジタルサービス法（DSA）により、**アプリ内課金で収益を得る開発者は
全員「トレーダー」**とみなされる。個人開発者の場合、

> 住所（または私書箱）・電話番号・メールアドレスの提供が必要で、
> **それらは App Store の製品ページに公開される**

つまり **PM の住所と電話番号が公開される。**

2025-02-17 以降、トレーダー情報を設定していないアプリは EU の App Store から
**実際に一斉削除された**。

あわせて EU 配信は **GDPR の対象**になる。医療情報を扱うアプリなので、
対応の重みは小さくない。

## その他の地域を外す理由

UI が日本語・英語のみで、サポートも日英しかできない。

## 順序について

**配信地域は後からいつでも広げられる。** 絞って出して、必要になったら
広げるのが安全。**逆（広げてから絞る）は既存ユーザーが購入できなくなる**ため
面倒になる。

## 期限

**内部テストの段階では急がない。公開前には必ず。**
