# 愛犬健康管理アプリ 機能仕様書（v0.2）

- 対象イベント：RevenueCat Shipaton 2026（2026年8月1日〜9月30日）
- 開発方針：AI駆動開発（複数エージェントによる並行実装）を前提に、機能単位で仕様を分離
- 収益モデル：無料版（広告あり／AI相談は回数制＋チケット追加購入）／有料版（広告非表示＋AI相談無制限）

**v0.2での変更点**
- 予防医療管理を「ワクチン」単体から「ワクチン／フィラリア予防／ノミ・ダニ予防」の統合管理に拡張（5章）
- 証明書登録にAI-OCR機能を追加（5.4章）
- 運用コストの見直しと費目別試算を新設（9章）

> 本書はAIエージェントへの実装指示書として利用することを想定し、機能ごとに「画面要件」「データ項目」「バリデーション／エッジケース」「他機能との依存関係」を明記しています。

---

## 0. 全体構成とエージェント分割案

複数エージェントで並行開発する場合、以下の単位に分割すると依存関係が少なく進めやすいです。

| Agent | 担当範囲 | 主な依存先 |
|---|---|---|
| Agent A：認証基盤 | ログイン・生体認証・アカウント／ペットプロフィール管理 | なし（他機能の前提） |
| Agent B：日常記録 | 健康記録（写真付き）・体重記録・トイレ記録 | Agent A（ペットID） |
| Agent C：医療管理 | 通院・薬・予防医療（ワクチン／フィラリア／ノミダニ、証明書AI-OCR含む） | Agent A（ペットID） |
| Agent D：AI機能 | AI相談・AI健康レポート／グラフ化 | Agent B・C（記録データの参照） |
| Agent E：課金・広告基盤 | RevenueCat連携（サブスク・チケット）、広告表示制御 | Agent A（ユーザーID）、Agent D（AI利用回数制御） |

**確認が必要な点**：エージェント間のデータ受け渡しはAPI契約（後述のデータモデル）を先に固定してから並行着手すると手戻りが少なくなります。着手前に全エージェント共通のスキーマ定義ファイル（例：OpenAPI）を用意することを推奨します。

## 1. ログイン・生体認証（Agent A）

### 1.1 概要
メールアドレス／SNSアカウントでの初回登録後、2回目以降の起動時は生体認証（Face ID／Touch ID／指紋認証）でログインできるようにします。

### 1.2 画面要件
- 初回登録画面：メールアドレス＋パスワード、または Apple／Googleアカウント連携
- 生体認証設定画面：初回登録直後に「生体認証を有効にしますか」を確認
- 起動時ログイン画面：生体認証プロンプト表示、失敗時はパスワード／PIN入力にフォールバック
- ペットプロフィール登録：犬種、名前、生年月日、性別、体重（初期値）、避妊去勢有無

### 1.3 データ項目
| 項目 | 型 | 必須 | 備考 |
|---|---|---|---|
| user_id | UUID | ○ | |
| email | string | ○ | ログインID |
| auth_provider | enum(email, apple, google) | ○ | |
| biometric_enabled | boolean | ○ | デフォルトfalse |
| pet_id | UUID | ○ | 1ユーザーに複数ペット登録可 |
| pet_name / breed / birthday / sex / neutered | 各種 | ○（体重除く任意） | |

### 1.4 バリデーション・エッジケース
- 生体認証が端末非対応／未設定の場合は自動的にパスワード認証のみの導線にする
- 生体認証の実装は端末のセキュアストレージに認証トークンを保存する方式とし、**生体情報自体（指紋データ等）はアプリ／サーバーで一切保持しない**設計にする（OS標準API：iOSはLocalAuthentication、AndroidはBiometricPromptを利用）
- 多頭飼い対応：1アカウントで複数ペットプロフィールを切り替えられるようにする（記録系機能すべてに影響）

**確認が必要な点**：SNS連携（Apple／Google）を必須にするか任意にするかは、審査対応の速さ（Appleは外部ログイン手段がある場合Sign in with Appleの提供が実質必須になるケースがある）を踏まえ、ストア審査ガイドラインを開発着手前に確認してください。

## 2. 写真付き健康記録（Agent B）

### 2.1 概要
日々の体調・皮膚の様子・食欲・便の写真などを記録するタイムライン機能です。

### 2.2 画面要件
- 記録一覧（タイムライン表示、日付降順）
- 新規記録画面：写真添付（複数枚、最大4〜6枚程度を想定）、カテゴリタグ選択、コメント入力
- 記録詳細画面：編集・削除

### 2.3 データ項目
| 項目 | 型 | 必須 | 備考 |
|---|---|---|---|
| record_id | UUID | ○ | |
| pet_id | UUID | ○ | |
| recorded_at | datetime | ○ | |
| photos | array\<url\> | 任意 | 複数枚、ストレージ上限を設定 |
| tags | array\<enum\> | 任意 | 皮膚／食欲不振／元気がない／嘔吐 等、複数選択可 |
| memo | text | 任意 | |

### 2.4 バリデーション・エッジケース
- 写真は端末側でリサイズ・圧縮してからアップロード（通信量・ストレージコスト削減のため）
- 1ペットあたりの写真保存容量に上限を設け、超過時は無料版では古い写真の圧縮表示、有料版では無制限、といった差別化も検討可能
- タグはAI相談機能（4章）の入力候補としても再利用する設計にすると開発効率が良い

**確認が必要な点**：写真ストレージ（Firebase Storage等）のコストは保存枚数に比例するため、無料版のアップロード上限（枚数／解像度）は事前にコスト試算した上で決定してください。

## 3. 体重記録（Agent B）

### 3.1 概要
定期的な体重測定値を記録し、推移をグラフで確認できる機能です。

### 3.2 画面要件
- 体重入力（日付・体重kg、小数点対応）
- 折れ線グラフ表示（期間切り替え：1ヶ月／3ヶ月／1年）
- 急激な増減時のアラート表示（任意）

### 3.3 データ項目
| 項目 | 型 | 必須 |
|---|---|---|
| weight_id | UUID | ○ |
| pet_id | UUID | ○ |
| measured_at | date | ○ |
| weight_kg | decimal(4,1) | ○ |

### 3.4 バリデーション・エッジケース
- 同日に複数回記録された場合は上書きか併記かをユーザー設定で選べるようにする
- 犬種・年齢別の適正体重レンジと比較する機能は将来拡張として切り出し、MVPでは「前回比」「1ヶ月前比」の増減表示に留めるのが現実的

## 4. トイレ記録（Agent B）

### 4.1 概要
排尿・排便の頻度、便の状態を記録し、体調変化の早期発見につなげる機能です。

### 4.2 画面要件
- ワンタップ記録（排尿／排便のボタン、記録時刻は自動入力）
- 便の状態選択（硬さ：正常／軟便／下痢／硬い、色：正常／血便疑い／白っぽい 等）
- 写真添付（血便など異常時の記録用、任意）
- 頻度グラフ（日別回数の推移）

### 4.3 データ項目
| 項目 | 型 | 必須 |
|---|---|---|
| toilet_id | UUID | ○ |
| pet_id | UUID | ○ |
| recorded_at | datetime | ○ |
| type | enum(urine, stool) | ○ |
| stool_condition | enum | 排便時のみ必須 |
| photo | url | 任意 |

### 4.4 バリデーション・エッジケース
- 「血便疑い」「下痢が◯日連続」等、特定条件が続いた場合にAI相談機能（4章）への導線を表示すると、AI相談機能への自然な誘導＝有料転換のきっかけになります
- 通知過多を避けるため、異常検知アラートの頻度には上限を設ける

## 5. 通院管理・薬・ワクチン記録（Agent C）

### 5.1 通院履歴
| 項目 | 型 | 必須 |
|---|---|---|
| visit_id | UUID | ○ |
| pet_id | UUID | ○ |
| visited_at | date | ○ |
| hospital_name | string | 任意 |
| diagnosis | text | 任意 |
| cost | integer | 任意 |
| next_visit_date | date | 任意（リマインダー用） |

### 5.2 薬の記録
| 項目 | 型 | 必須 |
|---|---|---|
| medication_id | UUID | ○ |
| pet_id | UUID | ○ |
| name | string | ○ |
| dosage | string | 任意 |
| start_date / end_date | date | ○（end_dateは任意＝継続中扱い） |
| reminder_enabled | boolean | ○ |
| reminder_time | time | reminder_enabled=trueの場合必須 |

### 5.3 予防医療管理（ワクチン／フィラリア予防／ノミ・ダニ予防）

ワクチンだけでなく、フィラリア予防・ノミダニ予防も同じ枠組みで管理できるよう、**予防プログラム（何を・どの頻度で行うか）**と**投与履歴（実際にいつ行ったか）**を分けたデータ構造にします。ワクチンは基本「単発＋次回予定日」、フィラリア／ノミダニ予防は「毎月投与」が主流という違いを、共通スキーマの中で吸収する設計です。

**予防プログラム（prevention_programs）** ＝ 何をどの頻度で行うかの設定

| 項目 | 型 | 必須 | 備考 |
|---|---|---|---|
| program_id | UUID | ○ | |
| pet_id | UUID | ○ | |
| type | enum(vaccine, heartworm, flea_tick) | ○ | 混合ワクチン／狂犬病ワクチンは vaccine 内のサブ種別として扱う |
| product_name | string | ○ | ワクチン名／予防薬名 |
| schedule_type | enum(single, monthly, annual, custom) | ○ | ワクチンは基本 single（都度登録）、フィラリア・ノミダニは monthly が主流 |
| interval_days | integer | schedule_type=customの場合必須 | |
| start_date | date | ○ | |
| active | boolean | ○ | 予防シーズン終了時などにfalseへ |

**投与履歴（prevention_records）** ＝ 実際に投与・接種した記録

| 項目 | 型 | 必須 | 備考 |
|---|---|---|---|
| record_id | UUID | ○ | |
| program_id | UUID | ○ | |
| pet_id | UUID | ○ | 記録一覧の検索を高速化するため非正規化して保持 |
| administered_at | date | ○ | 実施日 |
| visit_id | UUID | 任意 | 通院記録（5.1）と紐付ける場合 |
| hospital_name | string | 任意 | 通院と紐付けない自宅投与の場合に単独入力 |
| next_due_date | date | 任意 | monthly/annualの場合は interval_days から自動計算、手動上書きも可 |
| certificate_file | url（画像 or PDF） | 任意 | ワクチン証明書・検査結果票など |
| ocr_extracted_data | json | 任意 | AI-OCRによる抽出結果（5.4参照） |
| ocr_confidence | float | 任意 | 抽出結果の信頼度スコア |

**証明書表示機能の要件**：
- 一覧から証明書を即座に確認できるようにする（ペットホテル・ドッグラン・トリミング施設での提示を想定）
- オフラインでも証明書画像を表示できるよう、端末キャッシュを保持する設計が望ましい
- PDF・画像どちらの形式でもアップロード可能にする

**リマインダー**：`prevention_records.next_due_date` を元にバッチ処理でプッシュ通知を生成します。フィラリア・ノミダニ予防は「前回投与日＋interval_daysが近づいたら通知」、ワクチンは「登録されたnext_due_dateの◯日前に通知」という2パターンを共通ロジックで扱えます。

### 5.4 証明書のAI-OCR機能

**概要**：ワクチン証明書、フィラリア検査結果票、ノミダニ予防の証明書などを撮影するだけで、薬剤名・実施日・次回予定日・動物病院名といった主要項目を自動抽出し、入力フォームに反映する機能です。

**処理フロー**：
1. ユーザーが証明書を撮影／画像・PDF選択
2. 端末側で画像をリサイズ・圧縮してから送信（通信量とAPIコスト削減のため、送信前の軽量化は必須）
3. Claude Haiku 4.5（画像入力に対応したモデル）に画像を渡し、項目を構造化データ（JSON）として抽出するプロンプトを実行
4. 抽出結果をフォームに自動入力し、**ユーザーが必ず確認・修正してから保存**（誤読対策として、確認前の自動保存はしない）
5. 元画像／PDFは certificate_file として、抽出結果は ocr_extracted_data として保存

**バリデーション・エッジケース**：
- 手書き文字や不鮮明な画像では読み取り精度が下がるため、`ocr_confidence` が閾値未満の場合は「読み取れませんでした。手動で入力してください」というフォールバック導線を用意する
- PDF形式の証明書は1ページ目を画像化してから同様の処理を行う
- OCR結果はあくまで補助であり、最終的な記録内容の正しさはユーザー確認に委ねる設計とする（医療情報の誤登録を防ぐため）

**確認が必要な点**：Claude APIの画像入力（vision）における現行の料金換算方式（画像サイズとトークン数の対応）は変更される可能性があるため、実装時に公式ドキュメントで最新の計算式を確認してください。

### 5.5 バリデーション・エッジケース（通院・薬・予防医療 共通）
- 薬・予防医療のリマインダーはプッシュ通知で実装し、OSごとの通知許可フローを別途考慮する
- 通院履歴・薬・予防医療は互いに独立したエンティティとして持たせるが、UI上は「医療情報」としてまとめて閲覧できるタブを用意すると使いやすい

**確認が必要な点**：ワクチン証明書・検査結果は個人情報・医療情報に近い性質を持つため、保存先ストレージのアクセス制御（他ユーザーから閲覧できないこと）を必ず確認してください。

## 6. AI相談（Agent D）

### 6.1 概要
症状や気になる様子を入力すると、受診目安や考えられる原因の参考情報をAIが返す機能です。無料版は回数制限＋チケット追加購入、有料版は無制限とします。

### 6.2 画面要件
- 症状入力画面（テキスト入力＋トイレ記録・体重記録からのタグ引用も可能にする）
- AI回答表示（受診目安・注意点・免責事項を必ず併記）
- 相談履歴一覧
- 利用回数表示（残り◯回、チケット購入導線）

### 6.3 データ項目
| 項目 | 型 | 必須 |
|---|---|---|
| consultation_id | UUID | ○ |
| pet_id | UUID | ○ |
| question_text | text | ○ |
| referenced_records | array\<record_id\> | 任意（体重・トイレ記録等の参照） |
| ai_response | text | ○ |
| created_at | datetime | ○ |

### 6.4 利用回数制御
| プラン | 回数 |
|---|---|
| 無料版 | 月3回まで |
| チケット | 5回／15回パック（消耗型IAP） |
| 有料サブスク | 無制限 |

### 6.5 バリデーション・エッジケース
- **免責表示は必須**：「本機能は医療診断ではなく、受診目安の参考情報です」等の文言を回答画面に常時表示する
- 緊急性が高いと判断されるキーワード（けいれん、意識がない、誤飲 等）が入力された場合は、AI回答より先に「至急動物病院へ」という定型メッセージを優先表示する分岐を設ける
- APIコストを抑えるため、システムプロンプト（安全ガイドライン部分）はプロンプトキャッシュを活用し、モデルは軽量モデル（Haiku系）を基本とする

## 7. AI健康レポート・グラフ化（Agent D）

### 7.1 概要
体重・トイレ記録などの蓄積データをもとに、月次でAIによるサマリーレポートを生成する機能です（有料版の主要差別化要素）。

### 7.2 画面要件
- グラフ画面：体重推移、トイレ頻度推移（無料版でも基本グラフは閲覧可、有料版はAIサマリー付き）
- AIレポート画面：月次でのテキストサマリー（「今月は体重が◯kg増加しました。トイレの回数は先月と比べ◯回減少しています」等）
- PDF出力（通院時に獣医へ共有する用途を想定）

### 7.3 データ項目
| 項目 | 型 | 必須 |
|---|---|---|
| report_id | UUID | ○ |
| pet_id | UUID | ○ |
| period_start / period_end | date | ○ |
| summary_text | text | ○（AI生成） |
| generated_at | datetime | ○ |

### 7.4 バリデーション・エッジケース
- レポート生成は月1回のバッチ処理（サーバー側スケジューラ）とし、リアルタイム生成にしないことでAPIコストを抑える
- 有料版限定機能とするか、無料版でも簡易版（グラフのみ、AIサマリーなし）を出すかは差別化設計上の重要な分岐点

**確認が必要な点**：グラフ描画ライブラリ（Flutter採用の場合 fl_chart 等）は開発着手時点の最新安定版を確認してください。

## 8. 課金・広告基盤（Agent E）

### 8.1 概要
RevenueCat SDKを用いてサブスク・チケット（消耗型IAP）を管理し、広告表示は無料版のみに制御します。

### 8.2 商品構成案
| Product ID（例） | 種別 | 内容 |
|---|---|---|
| premium_monthly | 自動更新サブスク | 広告非表示＋AI無制限＋AIレポート |
| premium_yearly | 自動更新サブスク | 同上（年額割引） |
| ai_tickets_5 | 消耗型 | AI相談チケット5回分 |
| ai_tickets_15 | 消耗型 | AI相談チケット15回分 |

### 8.3 依存関係
- Agent Aが発行するuser_idに紐づけてRevenueCat上の顧客IDを管理
- Agent Dが管理するAI利用回数カウンターと連携し、購入検知時にチケット残数を加算する処理が必要

**確認が必要な点**：RevenueCatの手数料体系（月間トラッキング収益に応じた無料枠・従量課金の閾値）は変更される可能性があるため、開発着手前に公式サイトで最新条件を確認してください。

## 9. 運用コスト見直し

無料版の広告収入だけでインフラ・AI利用コストを賄うことを目標に、費目ごとに現状の設計とコスト削減策を整理します。数値はいずれも概算であり、実測での再検証が必要です。

| 費目 | 現状設計 | 概算コスト感 | コスト削減策 |
|---|---|---|---|
| AI相談（6章） | Haiku 4.5、月3回無料＋チケット | 1回あたり約0.3〜0.5円 | システムプロンプトのキャッシュ活用、緊急ワード検知は定型文で即返答しAPI呼び出し自体をスキップ |
| AI健康レポート（7章） | 月次バッチ生成 | 1件あたり数円未満 | **有料会員のみを対象に生成**（無料版はグラフ表示のみ）、月1回のバッチ処理に限定しリアルタイム生成をしない |
| 証明書AI-OCR（5.4章） | Haiku 4.5 vision、1匹あたり年数回程度 | 1回あたり数円未満（低頻度のため総額影響は小） | 送信前に画像をリサイズ・圧縮、信頼度が低い場合は即フォールバックし再送を防ぐ |
| 写真ストレージ（2章） | 健康記録・証明書の画像保存 | 保存枚数・解像度に比例 | 端末側でリサイズ・圧縮してからアップロード、無料版は保存枚数／解像度に上限を設定 |
| プッシュ通知 | ワクチン・薬・予防医療のリマインダー | FCM／APNsは無料 | 追加コストなし |
| バックエンド | サーバーレス構成 | 呼び出し量に比例、待機コストなし | アイドル時課金が発生する常時起動サーバーは避ける |
| DB／認証 | Firebase等の無料枠内運用を想定 | 小規模なら無料枠内 | 無料枠の上限（同時接続数・読み書き回数）を監視し、超過見込み時のみ有料プランへ |
| 課金基盤 | RevenueCat SDK | 収益規模に応じた手数料体系 | 無料枠の閾値を把握し、想定収益規模と照らして問題ないか事前確認 |

**乱用対策（コスト暴走の防止）**：
- AI相談・AI-OCRともに、1ユーザーあたりの短時間での連続呼び出しにレート制限を設ける
- 異常に大きい画像・長文の送信を防ぐため、クライアント側で送信サイズの上限を強制する
- AI関連のAPI呼び出し量を監視し、想定を超える利用が発生した場合にアラートが飛ぶ仕組み（使用量ダッシュボード等）を初期段階から組み込む

**確認が必要な点**：本表の単価はいずれも概算であり、実際のプロンプト長・画像サイズ・利用頻度によって変動します。開発着手後、実測値をもとに再試算し、無料版ユーザー数に対するAIコストの比率を継続的にモニタリングすることをおすすめします。

## 10. 非機能要件（共通）

- 対応OS：iOS／Android（Flutterでのクロスプラットフォーム開発を想定）
- オフライン対応：記録機能（健康記録・体重・トイレ）は端末ローカルにも一時保存し、通信復帰時に同期する設計が望ましい
- 多言語対応：Shipatonはグローバル参加者が対象のため、英語UIも視野に入れる場合は文言のi18n設計を初期段階から組み込む
- プライバシー：写真・ワクチン証明書等はユーザー本人以外がアクセスできないようアクセス制御を徹底する
